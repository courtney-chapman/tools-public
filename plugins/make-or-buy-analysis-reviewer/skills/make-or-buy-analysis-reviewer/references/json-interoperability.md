# Worksheet JSON handling

Accept compatible exported objects with `schemaVersion`, `requirement`, `makeAlternative`, `buyAlternative`, `hybridAlternative`, `costComparison`, `scheduleComparison`, `riskAssessment`, `smallBusinessConsiderations`, `formalProgram`, `decision`, and `supportingEvidence`. The published worksheet has exported schema `1.1`; other versions may differ. Read actual field values and identifiers rather than assuming that these groups contain complete evidence. In schema `1.1`, `hybridAlternative.enabled` controls whether the hybrid proposal was entered; `decision.choice` can be `Pending`; `formalProgram.applicability` can be `review`, `applies`, or `does-not-apply`. The `procurementReview` group may also appear.

For read-only review, do not rewrite the JSON. Cite paths such as `makeAlternative.capacity` and `decision.rationale` in findings when useful. Treat `Unknown`, blanks, and `null` as missing information, not negative answers. A numeric `0` is a supplied value and may need validation, not substitution. `supportingEvidence` records are references; inspect actual attachments only if provided and authorized. An itemized cost list and a single estimate may use different bases; flag a mismatch instead of replacing either value.

If asked to return updated JSON, use the supplied object and schema as the base. Preserve every original key, row ID, field identifier, value, ordering where practical, and unknown extension field. Change only fields the user explicitly asked to revise; provide a short change log. Do not silently migrate versions, fill blanks with invented values, or add review findings in unsupported schema fields. If the requested result cannot be represented safely in the supplied schema, return the original JSON unchanged and provide the findings separately or ask for the target field mapping.
